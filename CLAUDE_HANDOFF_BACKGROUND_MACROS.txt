0. DEMANDE NON NEGOCIABLE DU PROPRIETAIRE
======================================================================

Le moteur de macros doit pouvoir piloter plusieurs instances Roblox en meme
temps, qu'elles soient reduites ou non, sans jamais :

- restaurer, afficher, rendre transparente ou deplacer hors ecran une fenetre ;
- prendre le focus ;
- deplacer le vrai curseur Windows ;
- utiliser le vrai clavier ou la vraie souris ;
- envoyer des evenements globaux SendInput ;
- serialiser toutes les instances derriere un unique focus global ;
- utiliser Nexus pour les macros.

Chaque macro doit cibler exclusivement le couple PID + create_time de son
instance. Trois macros doivent pouvoir maintenir des touches, bouger trois
souris logiques, cliquer et utiliser la molette en parallele pendant que le
proprietaire utilise normalement son clavier, sa souris, Discord ou son
navigateur.

Un resultat visuellement proche ne suffit pas. Une fenetre restauree a alpha
1/255 est explicitement refusee. Une fonction n'est terminee que si la fenetre
reste IsIconic=true pendant toute l'action et que les peripheriques physiques
et le foreground restent inchanges.

2. REALITE TECHNIQUE A NE PAS MASQUER
======================================================================

Les API Win32 externes ordinaires ne fournissent pas de canal universel
"entree vers ce PID minimise" :

- PostMessage/SendMessage ciblent une file de messages HWND. Un jeu lisant Raw
  Input, DirectInput ou GetAsyncKeyState peut les ignorer.
- SendInput injecte dans le flux d'entree systeme : il est global, utilise le
  foreground et le curseur reel.
- un HWND minimise n'offre normalement plus une surface client exploitable
  pour un clic coordonne ; certains moteurs suspendent aussi leur boucle lors
  de SIZE_MINIMIZED.
- un peripherique HID virtuel est visible au niveau de la session. Sans couche
  de routage, chaque processus peut voir le meme peripherique ; ce n'est pas
  encore une association exclusive par PID.

Il n'y a que deux familles credibles pour satisfaire TOUT le besoin :

A. Hook interne par processus
   Intercepter Raw Input/GetAsyncKeyState/GetKeyboardState/curseur dans chaque
   processus et maintenir un etat clavier/souris virtuel propre a son PID.
   ProtoInput est la reference la plus proche, mais c'est bien une injection de
   DLL/hook. Cela peut etre bloque par Roblox. Ne jamais le presenter comme un
   simple SendInput magique.

B. Frontiere d'isolation
   Une VM ou une session Windows distincte par instance, avec un agent local
   qui emet les entrees dans cette session. Le bureau principal reste libre et
   chaque VM a son propre flux d'entree. C'est la piste sans injection dans le
   processus, mais elle est lourde (GPU, memoire, sessions Roblox, capture et
   orchestration).

Un bureau Windows cache cree par CreateDesktop n'est pas automatiquement une
solution : SendInput cible le desktop d'entree actif. Il faut le demontrer sur
un banc d'essai avant de le retenir.

3B. ALTERNATIVE PRIORITAIRE : DEVELOPPER ASTROINPUT
======================================================================

Le proprietaire propose de ne pas dependre de ProtoInput et de developper une
bibliotheque native sur mesure, limitee aux besoins d'Astro Account Manager.
Nom de travail : AstroInput.

OBJECTIF

AstroInput doit exposer un canal binaire par instance cible. MacroEngine envoie
des commandes semantiques a une session liee au couple PID + create_time :

- KEY_DOWN / KEY_UP ;
- TEXT_UTF16 ;
- POINTER_ABSOLUTE_CLIENT ;
- POINTER_RELATIVE ;
- BUTTON_DOWN / BUTTON_UP ;
- WHEEL_HORIZONTAL / WHEEL_VERTICAL ;
- RELEASE_ALL ;
- PING / CAPABILITIES / DETACH.

Ce ne doit PAS etre un canal d'execution de code arbitraire. Le mot
"instructions binaires" signifie ici un protocole binaire compact avec une
liste fermee d'opcodes d'entree, tailles bornees et validation stricte. Aucun
opcode ne doit permettre de lire/ecrire une adresse arbitraire, charger une DLL
quelconque, lancer un processus ou invoquer un script.

FRONTIERE TECHNIQUE A ASSUMER

Une DLL/EXE uniquement EXTERNE au processus ne peut pas forcer un jeu Raw Input
minimise a consommer un etat clavier/souris prive par PID. Elle ne pourrait que
faire PostMessage ou SendInput, donc echouerait au cahier des charges.

AstroInput a donc deux implementations possibles derriere la meme API :

1. AstroInputProcessAdapter
   Un module natif minimal execute dans le processus cible, qui intercepte
   uniquement les API d'entree dont le programme se sert et renvoie l'etat
   virtuel de SA session. C'est techniquement un hook/in-process adapter, meme
   si le code est ecrit par Astro. Ne jamais le masquer dans la documentation.

2. AstroInputSessionAdapter
   Un agent execute dans une VM/session Windows isolee. Le broker lui envoie le
   meme protocole, mais aucune DLL n'est chargee dans Roblox. Cette variante est
   plus lourde, mais constitue l'alternative propre si l'adaptateur in-process
   est refuse ou bloque.

ARCHITECTURE RECOMMANDEE

AstroInput separe quatre composants :

- astro_input_protocol : structures binaires, versionnage et validation ;
- AstroInputBroker.exe : processus enfant local lance par Astro ;
- astro_input_backend.py : binding Python vers le broker ;
- un adapter selectionnable : ProcessAdapter ou SessionAdapter.

Le broker maintient une InputSession independante par PID + create_time. Chaque
session contient :

- tableau atomique de 256 touches ;
- modifiers et sequence de texte ;
- position logique client X/Y et delta relatif ;
- etat des cinq boutons ;
- accumulateurs de molette ;
- numero de sequence monotone ;
- liste des capacites effectivement actives ;
- heartbeat, etat attached/detaching/dead ;
- journal d'ACK borné sans contenu secret.

PROTOCOLE BINAIRE

En-tete fixe propose :

  magic[4]      = "AINP"
  version_u16
  opcode_u16
  payload_len_u32
  session_id_u64
  sequence_u64
  monotonic_ns_u64
  flags_u32
  crc32_u32

Chaque opcode a un payload fixe ou strictement borne. Le parseur refuse avant
toute mutation : mauvais magic/version, taille incoherente, sequence rejouee ou
hors ordre, valeur NaN, coordonnee hors borne, touche inconnue, session morte et
PID/create_time ne correspondant plus.

Transport recommande : named pipe Windows duplex avec ACL du SID CurrentUser,
nom aleatoire par lancement, authentification challenge-response locale et
handshake de version. Le secret du challenge ne figure ni dans argv, ni dans
les logs, ni dans SQLite. La memoire partagee/ring buffer ne doit etre ajoutee
qu'apres mesure montrant que le pipe est insuffisant ; la fiabilite importe plus
qu'une micro-optimisation prematuree.

ADAPTATEUR PROCESSUS

Ne pas recopier ProtoInput en entier. Construire seulement les adaptateurs
necessaires, chacun active par capability probe :

- GetAsyncKeyState/GetKeyState/GetKeyboardState : lire l'etat atomique propre a
  la session ;
- GetCursorPos/SetCursorPos/ClipCursor : exposer uniquement le curseur logique
  de la session sans toucher au curseur Windows ;
- WM_KEY*/WM_MOUSE* : produire depuis le thread/processus cible si le banc
  prouve que l'application les consomme ;
- Raw Input : adapter RegisterRawInputDevices/GetRawInputData et la notification
  WM_INPUT seulement si la trace prouve ce chemin. Les objets/tokens Raw Input
  synthetiques doivent etre internes a l'adaptateur et ne jamais etre confondus
  avec des HRAWINPUT systeme reels ;
- focus logique : capability separee. Ne pas mentir sur IsIconic. La fenetre
  doit rester reellement minimisee et l'adaptateur doit refuser si la boucle du
  programme ne traite plus rien dans cet etat.

Le hook doit etre non bloquant : les appels du jeu lisent un snapshot atomique.
Le thread du pipe met l'etat a jour. Aucun appel Python, disque, reseau ou lock
long dans un hook. Un detach ou crash broker replace l'etat virtuel a zero.

API PYTHON SUGGEREE

  broker.probe() -> BrokerCapabilities
  broker.attach(pid, expected_create_time) -> InputSession
  session.key_down(vk, scan_code=0)
  session.key_up(vk, scan_code=0)
  session.text(value)
  session.pointer_abs(x_normalized, y_normalized)
  session.pointer_rel(dx, dy)
  session.button_down(button)
  session.button_up(button)
  session.wheel(dx=0, dy=0)
  session.release_all()
  session.capabilities()
  session.close()

Chaque methode attend un ACK "accepted" puis, si le banc peut l'observer, un
ACK distinct "observed". Un ACK accepted seul ne constitue jamais une preuve
que le jeu a consomme l'entree.

PARALLELISME

Il faut un worker/queue par session. A maintient W pendant que B maintient A et
que C clique : les trois etats coexistent. Aucun verrou global d'entree. Seul le
transport peut multiplexer brièvement les paquets ; il ne doit pas serialiser
la duree des actions. Les sequences sont independantes par session.

SECURITE ET ROBUSTESSE

- allowlist stricte de l'executable cible et verification de sa signature/chemin ;
- PID + create_time verifies avant chaque attach et periodiquement ;
- broker en utilisateur standard, jamais service SYSTEM ;
- ACL CurrentUser et aucun port TCP ;
- aucune primitive generale de memory read/write ou remote thread dans l'API
  exposee a MacroEngine ;
- limites de frequence, taille de texte, deltas, files et memoire ;
- release-all automatique sur cancel, detach, timeout et fermeture d'Astro ;
- crash containment : un adapter defectueux ne doit pas corrompre SQLite/vault ;
- journaux sans cookies, tokens, mots de passe ou contenu sensible saisi.

LICENCE ET BUILD

Ecrire AstroInput depuis zero permet de choisir une licence compatible avec le
projet et d'eviter la GPL de Nucleus. Si des portions ProtoInput MIT inspirent
une implementation, conserver les notices requises et documenter precisement
la provenance. Le build C/C++ x64 doit etre reproductible, epingle et integre a
scripts/build_windows.py. Archiver commit, toolchain, taille et SHA-256.

DECISION GATE

AstroInputProcessAdapter n'est integre a Roblox que si :

- il passe d'abord toutes les preuves sur input_lab A/B/C ;
- aucun SendInput/SetCursorPos/SetForegroundWindow/ShowWindow n'est importe ou
  appele dans le chemin strict ;
- les trois fenetres restent IsIconic=true ;
- la saisie et le curseur physiques restent independants ;
- trois etats simultanes distincts sont observes ;
- la compatibilite Roblox est demontree sans tentative de contourner un blocage
  de protection. En cas de blocage, basculer vers SessionAdapter/VM ou marquer
  la capacite indisponible.

Cette voie est probablement la meilleure architecture produit si Claude veut
un controle complet, un protocole minimal, des tests fiables et aucune
dependance opaque. Elle ne supprime toutefois pas le fait fondamental que le
mode ProcessAdapter execute une couche dans le processus cible.
